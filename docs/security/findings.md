| F-026 | MEDIUM | Sprint 26 | `packages/agent-runtime-worker/src/mission-copilot-tools.ts` (Family D/E tools) | **Every Family D/E mutating tool except `SaveMissionConfig` has no confirmation gate and no resume-delay grace period** — `PauseAgent`, `ResumeAgent`, `CreateScheduledMessage`, `CancelScheduledMessage`, `CancelBackgroundJob`, `RestartBackgroundJob`, and `SetMissionSpendCap` (see F-025) are all immediate on call, with a same-turn audit-trail mailbox post as the only check a human gets. | F-029 | LOW | Backlog | `packages/agent-runtime-worker/src/loop.ts` (`runInnerLoop`'s `sessionId` → `x-session-id` header, ADR-0024) | **An `agentId`/`missionId` containing a control character (e.g. CR/LF) would crash the turn instead of degrading gracefully** — `sessionId` is built as `` `${missionId}:${agentId}` `` and passed to pi-ai as `options.sessionId`, which OpenRouter models send verbatim as the `x-session-id` header. Verified (not assumed): Node's own `http` module throws `ERR_INVALID_CHAR` synchronously on `setHeader` for an invalid header value, so this is **not an exploitable header-injection vector** (Node blocks it at the transport layer) — but the resulting exception propagates uncaught out of `runInnerLoop` to the orchestrator's crash handler, turning a malformed-but-non-malicious ID (e.g. from a future config source with looser validation) into a full turn crash instead of a clean validation error at config-load time. | Either tighten `mission.id`/`agent.id` to a slug pattern in the Zod schema (defense in depth, also improves error messages elsewhere IDs are used in paths/headers), or sanitize/strip control characters from `sessionId` specifically before passing it to `completeSimple` in `loop.ts`. | F-031 | LOW | Sprint 28g | `packages/control-plane/src/resource-upgrade.ts`, `mission-copilot-router.ts` (`POST /resources/upgrade`), `packages/agent-runtime-worker/src/mission-copilot-tools.ts` (`RequestResourceUpgrade`) | **The mission-copilot can replace its mission's machine with a larger, paid one without operator confirmation** (ADR-0031, TB-22) — the same class as F-025/F-026 (an execution-plane copilot tool that acts immediately, with a mailbox audit message as the only human-facing check), but the effect is a hard restart of the mission plus machine cost that the LLM spend cap does not cover. Mitigated by bounds that hold even if the copilot's judgment fails, so this is recorded as LOW rather than MEDIUM: maximum 4 CPUs / 16 GB (control-plane constant), mandatory duration ≤ 60 min per window, 24 h cumulative upgraded-runtime cap that only the operator can reset (Firebase-authenticated route, writer separate from every execution-plane path), 5-min cooldown between shape changes, one resize at a time, every change posted to the operator, and a hard `upgrade-cap-reached` alert. Worst case is roughly $6 per reset cycle (24 h at the largest shape, display price table). Worker agents cannot call the tool at all — they can only ask the copilot. | A confirmation gate is the same work as F-021/F-023/F-026 (a confirmable UI surface for execution-plane copilot actions, CR-07); until then the structural bounds are the mitigation and are documented, not assumed sufficient. Optionally require operator confirmation for the first upgrade of a mission. |

## Accepted Findings

Accepted as design trade-offs. Re-evaluate before production deployment.

| ID | Severity | File | Description | Rationale |
|----|----------|------|-------------|-----------|
| A-001 | MEDIUM | `workspace-manager.ts` | **sharedDir shared write surface** — all agents in a mission have `rwx` on `sharedDir`, so any agent can overwrite another's output or modify mission skills. | Intentional design: agents collaborate via shared files. The alternative (per-agent skill dirs) defeats the purpose of shared skills. Mitigated by AclPolicy on workdirs. |
| A-002 | LOW | `tools.ts:D1` | **Bash has no software checkPath** — path enforcement for Bash is delegated entirely to OS Linux ACLs, not to `checkPath()`. | Correct by design: Bash runs as the agent's linuxUser and OS ACLs enforce the boundary. A software check would be redundant and bypassable anyway. |
| A-003 | LOW | `tool-api-server.ts` | **MAGI_TOOL_TOKEN appears in job log files** — if a job script runs `env`, the token appears in `logs/bg-<id>.log`. | Token is short-lived (revoked on job exit). Logs are within `sharedDir` (agent-accessible but not externally exposed). No urgent fix. |
| A-004 | INFO | `prompt.ts` | **Mailbox message bodies are injected into agent context unescaped** — a compromised agent can send adversarial instructions to other agents via PostMessage. | Intended mechanism for agent communication. Technical mitigation would break the system. Defended by agent role prompts treating messages as task instructions, not unconditional directives. |
| A-005 | INFO | `daemon.ts:A4` | **Agent can queue a background job via `submit-job.sh`** — job runs as the agent's own linuxUser and receives `MAGI_TOOL_TOKEN`. | The job has the same OS privileges as the agent's Bash tool. The token maps to the agent's own AclPolicy — no escalation beyond what the agent already has. |
| A-006 | LOW | `anomaly.ts`, `orchestrator.ts` (system mail) | **AN1 — agent-influenced text (error messages, job paths) is quoted inside system-originated anomaly mail without untrusted-content markers.** | Accepted 2026-10-18 (operator decision). Markers on web content are labels, not sanitisers: once an agent has read an injected page, everything it writes afterwards (mail, files, notes, errors) can carry the instruction, and agent-to-agent mail is already unmarked by design (A-004). Marking one more path adds little. Mitigation is structural instead: no credentials in agent/job environments, ceilings and caps no agent can raise, operator confirmation for external writes, path/egress guards — plus the planned independent auditor agent (roadmap) for detection. |
| A-007 | LOW | `objectives/agent-view.ts` (`renderMyObjectives`) | **OV2 — objectives text (including agent-written task notes) is injected into every assignee's mental map without provenance markers or a size cap.** | Accepted 2026-10-18, same reasoning as A-006. |
| A-008 | LOW | `mission-copilot-tools.ts` (`SaveMissionConfig`) | **MC1 — the mission copilot can rewrite any agent's prompt, disabled tools and limits in its mission.** | Accepted 2026-10-18: configuring the team is the copilot's job. Bounded by the spend ceiling it cannot write, announced to the operator in an audit message on every change, and applied only at the next resume. |
