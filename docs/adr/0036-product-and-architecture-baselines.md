# ADR-0036: Product and architecture baselines as a typed catalog

**Status:** Proposed (2026-11-15). The product owner's decisions Q-01 to Q-10 below were made
on 2026-11-14; the catalog's content is a draft awaiting their approval.
**Relates to:** [magi-dev-requirements.md](../plans/magi-dev-requirements.md) ("The application
model"), the code-structure practice ("One operation, one home"), ADR-0021 (structured mission
config), the env catalog (`docs/env.md`)

## Context

MAGI DEV's reviewer agents compare what MAGI is meant to do with what the code does. Their first
runs failed for two reasons: there was no agreed statement of intent to compare against, and
they traced calls by reading rather than with tools. The fix has two halves:

- **Intended:** actors, entities and their states, operations and their rules, journeys, and the
  components the software is built from, approved by the product owner.
- **As built:** scans (CodeQL, dependency-cruiser, git history) that list entry points, the code
  each one reaches, status writes and dependencies.

The scans must join their results to the intended model by id: an entry point to its operation,
a file to its component, a status write to an entity's transition, a test to a journey. Markdown
tables are readable but brittle as script input, and the join keys have to be checked, not
trusted.

## Decision

1. **The baselines are a typed catalog in `packages/agent-config/src/baseline/`**: actors,
   components (with path patterns and dependency rules), entities (with where each is stored,
   its states, intended transitions and invariants), operations (with actors, intended home
   component and rules) and journeys. Scripts and tests read the catalog, never the documents.
2. **The documents are rendered from it.** `docs/product/{actors,entities,operations,journeys}.md`
   and `docs/architecture/components.md` are generated by `npm run docs:baseline`; a unit test
   fails when they are stale, as `docs/env.md` is kept in step with the env catalog. Only
   `docs/product/README.md` is written by hand.
3. **References are checked by the compiler.** Operation, actor, component, state and journey
   ids are literal types, so an operation naming an unknown home, a journey naming an unknown
   operation, or a transition naming an undeclared state fails `tsc`. Code that tags an entry
   point with an operation id will import `OperationId` the same way.
4. **The test checks what the compiler cannot:** unique ids; every source file under a
   component root in exactly one component; no path pattern that owns nothing; every operation
   in a journey or on a reviewed list of exceptions.
5. **Where the code and the catalog disagree, neither is edited quietly.** The difference is a
   finding against the code, or a question for the product owner about the baseline. A change to
   the catalog is approved by the product owner.
6. **One home per fact.** The SPEC describes mechanisms and cites baseline ids instead of
   restating states or operation rules; ADRs record why a baseline changed and name the ids
   affected; plans propose baseline changes; the roadmap schedules them.

## Product decisions adopted with this baseline (2026-11-14)

| Id | Question | Decision |
|---|---|---|
| Q-01 | A schedule falls due while its mission is suspended | Wake the machine; it stays running, and the operator is told what woke it |
| Q-02 | A mission in `error` | The control copilot recovers it on its own, within a budget the platform enforces, and decides when it needs human help: when the budget is spent, when it is unsure of the cause, or when the fix goes beyond restoring a known-good state. No doom loop: a failed attempt is never repeated without a new diagnosis |
| Q-03 | Creating schedules | Both: the intended way is through the copilot, and the operator can also define a schedule by hand in the cockpit |
| Q-04 | Changing a mission's configuration | Changes that can be applied while agents run are applied without suspending; suspending is a last resort for changes that need all activity stopped |
| Q-05 | How a mission ends | Suspend is the end state until archive exists; archive stops all costs and keeps the results readable; missions are not deleted (decision D-6) |
| Q-06 | Who may pause an agent | The operator and the copilots only; a supervisor agent works with the agents it oversees through the mailbox |
| Q-07 | A paused agent across a restart | It stays paused |
| Q-08 | Which configuration changes need all activity stopped | A change of machine size or of the agents roster |
| Q-09 | Keeping a mission's status in step with its machine | Continuously, by the platform on a timer, as one operation; reads only read |
| Q-10 | A machine that stops or disappears without a suspend | The mission goes to `error` with the reason, which brings in the copilot's recovery (Q-02); it is not shown as suspended |

## Alternatives considered

- **Hand-written markdown only.** Readable, but scripts would parse tables, and nothing would
  catch a misspelled id in the code or a journey naming a retired operation.
- **YAML files with a schema.** Machine-readable and checked at test time, but ids would not be
  types: a tag in the code could not be checked by the compiler.
- **A requirements tool (StrictDoc, OpenFastTrack, Doorstop).** Built for large regulated
  baselines with many hundreds of requirements; another toolchain for a baseline of about 60
  items. Revisit if the baseline outgrows the catalog.

## Consequences

- The baselines live in a runtime package. They are types and constants only, with no runtime
  effect, in the package that already holds the shared contract (stored types, the env catalog).
- Editing the baseline means editing TypeScript and running `npm run docs:baseline`, which is
  the same path the coding agent takes for env vars.
- Prose that is not tied to an id (the reasoning behind a decision) stays in ADRs and the README,
  not in the catalog.
- The code's `MissionStatus` includes `destroyed`, which the baseline does not intend (missions
  are not deleted). The status-write scan will report it; resolving it is a code change for a
  later sprint.
