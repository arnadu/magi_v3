# Usability checklist

Nielsen's ten usability heuristics, made specific to MAGI's cockpit and copilot
conversations, plus four MAGI checks (UX-11 to UX-14). Answer each row for the surface or
journey under review. Verdicts: pass · fail · missing · n/a · unverifiable — each with evidence
(the screen and component, or the transcript turn).

| Id | Heuristic | Check | Verdict | Evidence |
|---|---|---|---|---|
| UX-01 | Visibility of status | After every operator action (a click, a confirmed card, a message), the operator sees within seconds what happened and what comes next | ? | |
| UX-02 | Visibility of status | A copilot never goes quiet while work it started is pending; long operations (launch, resume, upgrade) show progress or a promise of when they will report | ? | |
| UX-03 | Real-world language | Screens and messages use the operator's words (mission, draft, agent, cap) rather than internal ids, codes or stack traces; ids appear only where the operator needs them | ? | |
| UX-04 | Control and freedom | The operator can cancel or undo: dismiss a card, edit a draft before launch, stop a runaway agent or mission, revert a change | ? | |
| UX-05 | Consistency | One action has one name across the cockpit, the copilots, the cards and the documentation; similar screens behave alike | ? | |
| UX-06 | Error prevention | Invalid input is refused before anything is confirmed or saved; costly or destructive actions need an explicit confirmation that states the consequence; defaults are safe | ? | |
| UX-07 | Recognition over recall | The operator chooses from options (templates, agents, models with prices) instead of having to remember ids, commands or formats | ? | |
| UX-08 | Efficiency | The journey takes the fewest confirmations, messages and screens the safety rules allow; repeated tasks have a shortcut | ? | |
| UX-09 | Minimalism | Messages are short and not repeated (no copilot reply sent twice, no stream of routine system notices); screens show what matters first | ? | |
| UX-10 | Recovery from errors | Every error says what happened, why, and what to do next; a copilot that hits an error proposes the fix itself | ? | |
| UX-11 | Help | Help is where the operator needs it: in-screen hints, the copilot can explain any screen or term, the how-to is linked | ? | |
| UX-12 | Trust | Confirmation cards show exactly what will change and what it costs; the operator can see afterwards who changed what and when | ? | |
| UX-13 | Cost | Spend against cap is visible per mission, warnings come before the cap is hit, and model choices show their price | ? | |
| UX-14 | Notifications | Events the operator must act on reach them promptly; everything else stays out of their inbox | ? | |
